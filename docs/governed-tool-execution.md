# Governed Tool Execution

## Contract

A model or agent may propose a registered tool and JSON input. A proposal is not permission to execute. Unknown tools and malformed input are rejected. Every execution passes through the existing runtime, which checks the declared capability and authorization policy and records execution evidence and events.

Tool definitions require an explicit resource, action, capability, handler, and approval policy. Consequential tools require a separate application-mediated approval step by default. The application must show the user the tool name, purpose, and proposed arguments before invoking `router.approve(proposalId)`. Never expose the approval method as a model-callable tool, and never interpret text generated by a model as user approval. The API assumes that only trusted host UI code calls `approve`; it does not cryptographically authenticate a human.

Only tools explicitly registered by the host can run. There is no generic shell, arbitrary code execution, or unrestricted filesystem tool. A read-only tool may set `requiresApproval: false` only when its behavior and resource scope are genuinely read-only and narrowly bounded.

## Example

```js
import { createAuthorizationPolicy } from '../src/authorization.mjs';
import { createCapability } from '../src/capability.mjs';
import { createEventLog } from '../src/event.mjs';
import { createRuntime } from '../src/runtime.mjs';
import { createToolDefinition, createToolRegistry, createToolRouter } from '../src/tool-router.mjs';

const events = createEventLog();
const policy = createAuthorizationPolicy({
  rules:[{subject:'personal-assistant',resource:'notes',action:'read',effect:'ALLOW'}]
});
const runtime = createRuntime({authorizationPolicy:policy,eventLog:events});
const registry = createToolRegistry();
registry.register(createToolDefinition({
  id:'notes.read', resource:'notes', resourceType:'note', action:'read',
  capability:createCapability({id:'notes.read',action:'read',resourceType:'note'}),
  requiresApproval:false,
  handler:({noteId}) => ({noteId,content:'Example note'})
}));
const router = createToolRouter({runtime,registry,eventLog:events});
const proposal = router.propose({toolId:'notes.read',input:{noteId:'example'}});
const result = router.execute(proposal.id);
```

## Audit and privacy

Proposal audit events include the tool identifier, action, approval requirement, and input field names, not raw input values. Runtime execution events follow the existing runtime contract, which may include tool results. Tool authors must therefore avoid returning secrets or unnecessary personal data from handlers, and host applications must treat event logs as potentially sensitive local data.

## Current limits

This layer is synchronous and in-process. It does not provide OS sandboxing, cryptographic user identity, durable approval records, background execution, or a desktop confirmation dialog. Those are separate host-application responsibilities and must not be implied by this API.
